# Deploy and release process

Applies to every service. This describes how a change reaches production. It
does not describe how to undo one during an incident — each service has its own
rollback runbook, and during an incident that runbook takes precedence over
anything written here.

## The pipeline

1. Pull request, with at least one approving review from a code owner.
2. CI: unit tests, integration tests, a container build, and a vulnerability scan.
3. Automatic deploy to staging on merge to `main`.
4. Smoke suite against staging. A failure here blocks the production stage.
5. Production deploy, which is a **manual promotion** — someone presses the button.
6. Canary at 10% of traffic for 15 minutes, watched automatically against error
   rate and p95 latency. A breach rolls the canary back without human involvement.
7. Full rollout.

## Deploy windows

Deploys are allowed 09:00–16:00 on working days. This is a window, not a
prohibition: outside it, deploying requires the on-call engineer to be informed
first, so that whoever is holding the pager knows a change is in flight.

Deploys are frozen entirely during declared peak commercial periods. The freeze
calendar is published a quarter ahead.

## Database migrations

Migrations follow expand-and-contract, always in two separate releases:

- **Expand.** Add the new column, table, or index. Deploy. The new column is
  nullable and the old code ignores it.
- **Contract.** Only after the expanding release has been stable in production
  for at least one full week, remove the old column.

Never ship a destructive migration in the same release as the code that stops
using the thing being dropped. Doing so makes that release unrollable, which is
precisely the situation the rollback runbooks warn about.

## Feature flags

Anything risky ships behind a flag, defaulting to off. A flag change takes
effect within thirty seconds and does not require a deploy, which makes it the
fastest mitigation available during an incident.

Flags are not permanent. Every flag carries an owner and a removal date.

## Release notes

Every production deploy writes a release note recording what changed, whether a
migration was included, and whether it was additive or destructive. During an
incident this note is the first thing the responder reads, so it is written for
that reader.
