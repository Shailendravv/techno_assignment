# Postmortem: checkout-api outage, 2026-08-10

**Severity:** SEV1
**Duration:** 47 minutes (14:12–14:59 UTC)
**Impact:** Approximately 8,400 checkout attempts failed. Customers saw a
generic error at the payment step. No orders were double-charged and no data
was lost.

This is a record of one specific incident. For the general procedure to follow
when this failure mode recurs, see the checkout-api connections runbook.

## What happened

At 14:12 UTC, checkout-api began returning 500s on `/checkout`. The
`checkout-api-5xx-rate` alert fired at 14:14 and the primary on-call
acknowledged at 14:15.

Logs showed `FATAL: sorry, too many clients already` from the checkout Postgres
primary, and `QueuePool limit of size 30 overflow 10 reached` in the
application. `/health` continued to pass throughout, because the health check
does not take a database connection — so Kubernetes kept the pods in service
while every real request failed.

## Root cause

**Connection pool exhaustion, caused by a deploy that changed replica count
without changing pool size.**

Release `checkout-api@2026.08.10-1` was promoted at 14:09. It raised the HPA
minimum from 4 replicas to 12 in order to prepare for a scheduled promotion. The
per-pod connection pool remained at its existing size of 30, with an overflow of
10.

Twelve replicas at 40 maximum connections each is 480 connections. The checkout
Postgres primary is configured with `max_connections = 200`. The pool exhausted
within three minutes of the new pods reaching readiness.

The arithmetic — total connections are replicas multiplied by pool size — was
not checked because replica count and pool size are configured in two different
files, owned in practice by two different people.

## Contributing factors

- **The canary did not catch it.** The canary ran at 10% of traffic with two
  pods, which stayed comfortably inside the connection budget. The failure only
  appears at full replica count, which is after the canary gate.
- **The health check was misleading.** It did not exercise a database
  connection, so unhealthy pods continued to report healthy.
- **No alert on connection saturation.** We alerted on the symptom (5xx rate) and
  not on the cause. An alert at 80% of `max_connections` would have fired before
  any customer was affected.

## Resolution

At 14:51 the responder correlated the outage with the 14:09 release and rolled
back to the previous revision. Replica count returned to 4, connections fell
below the limit, and error rate returned to baseline by 14:59.

Rollback was safe because the release contained no database migration.

## What we changed

1. `max_connections` capacity is now validated in CI against
   `replicas x pool_size` for every service, and the build fails if the product
   exceeds 80% of the primary's limit.
2. The checkout-api readiness probe now takes and returns a database connection.
3. An alert fires at 80% of `max_connections` on every Postgres primary.
4. Replica count and pool size were moved into the same configuration file.
