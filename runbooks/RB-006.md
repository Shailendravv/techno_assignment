# Runbook: payments-api — Rollback procedure

## When to roll back

Roll back when a payments-api release correlates with elevated error rate,
latency, CPU, memory, or connection use, and the cause is not immediately
obvious. Rolling back first and diagnosing afterwards is the expected behaviour
during an incident — you do not need approval to roll back.

## Before you start

1. Confirm which release is live: `kubectl rollout history deploy/payments-api`.
2. Note the revision number you intend to return to, and the image tag it uses.
3. Check the release notes for that window. If the deploy included a **database
   migration**, stop and read the next section before doing anything.
4. Check whether any payment is mid-authorisation. Rolling back during an open
   authorisation window can leave a transaction in an indeterminate state with
   the provider, and reconciliation will not fix it for you.

## Database migrations

This is the part that makes rollback unsafe if skipped.

payments-api migrations are expand-and-contract. A rollback is safe if the
migration was **additive** (a new nullable column, a new table, a new index) —
the old code ignores what it does not know about.

A rollback is **not** safe if the migration was **destructive** (a dropped
column, a renamed column, a narrowed constraint). The previous release will
query columns that no longer exist and fail on every request. In that case, roll
the migration back first, or fix forward instead. Ask the database on-call if
you are unsure — that is faster than finding out.

## Rolling back

```
kubectl rollout undo deploy/payments-api --to-revision=<N>
kubectl rollout status deploy/payments-api --timeout=300s
```

Watch the payments-api Grafana board as pods cycle. Error rate should fall
within two minutes of the new pods passing readiness.

## Verifying

1. Error rate on `/authorize` returns to baseline.
2. p95 latency returns below 300ms.
3. A test authorisation and capture complete against the provider sandbox.
4. Settlement reconciliation for the current window shows no orphaned records.
5. The originating alert clears on its own rather than being silenced.

## Afterwards

Because payments is a regulated service, every rollback is recorded in the
change log with an accompanying reason, whether or not it caused customer
impact. Open an incident record — see the incident communication policy.
