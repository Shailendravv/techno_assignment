# Runbook: payments-api — High CPU

## Symptoms

Sustained CPU above 85% on payments-api pods for more than five minutes.
Request latency on `/authorize` and `/capture` climbs above the 300ms p95 target.
The `payments-api-cpu-high` alert fires in PagerDuty. Horizontal pod autoscaling
may already have scaled the deployment to its ceiling of eight replicas without
bringing utilisation down.

## First checks

1. Check the deploy log for a recent release. `kubectl rollout history deploy/payments-api`.
   The large majority of CPU incidents on this service follow a deploy within the previous hour.
2. Open the payments-api Grafana board and compare CPU against request rate. If CPU has
   risen while request rate has stayed flat, the cause is the code, not the traffic.
3. Check whether settlement batch processing is running. The nightly settlement job
   shares the pod pool and is CPU-heavy; overlap with peak traffic causes this.
4. Confirm the node pool is not oversubscribed. A noisy neighbour on the same node
   presents identically from inside the pod.

## Diagnosis

Take a CPU profile from one hot pod:

```
kubectl exec -it <pod> -- py-spy record -o /tmp/profile.svg --pid 1 --duration 30
```

Look for time concentrated in cryptographic signing of provider requests, retry
loops against a slow payment provider, or regular-expression matching in request
validation. Those three account for most CPU regressions we have seen in this service.

## Mitigation

If a deploy correlates, roll it back — see the rollback runbook. Rollback is
preferred over scaling, because scaling a CPU-bound regression raises cost
without fixing latency.

If the settlement batch correlates, pause the batch. It is designed to be
resumable and will catch up without manual intervention.

If neither correlates and traffic is genuinely elevated, raise the HPA ceiling
temporarily and open a capacity ticket.

## Escalation

Payments is a regulated service. If CPU is not recovering ten minutes after
mitigation, escalate immediately to the Payments team's secondary on-call and
notify the payments engineering manager. See the escalation policy.
