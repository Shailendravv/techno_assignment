# Runbook: checkout-api — Too many connections

## Symptoms

checkout-api logs fill with `FATAL: sorry, too many clients already` or
`remaining connection slots are reserved`. Application logs show
`QueuePool limit of size 20 overflow 10 reached, connection timed out`.
Requests to `/checkout` return 500 while `/health` continues to pass, because
the health check does not take a database connection. The
`checkout-api-5xx-rate` alert fires.

## Likely cause

Connection pool exhaustion against the `checkout` Postgres primary. In every
incident we have recorded, the cause has been one of three things:

1. **A deploy that raised replica count without lowering per-pod pool size.**
   Total connections are `replicas × pool_size`. Twelve replicas at pool size 30
   is 360 connections against a primary configured for `max_connections = 200`.
   This is the most common cause by a wide margin.
2. **A slow query holding connections open.** One unindexed query on a large
   table will hold its connection for its whole duration, and the pool drains.
3. **A connection leak** — a code path that takes a connection and does not
   return it, usually an error path that skips the context manager.

## First checks

1. Count current connections:
   `SELECT count(*), state FROM pg_stat_activity WHERE datname='checkout' GROUP BY state;`
   A large `idle in transaction` count points at a leak. A large `active` count
   points at slow queries.
2. Check the deploy log. `kubectl rollout history deploy/checkout-api`.
   Correlate against the replica count at the time.
3. Find long-running queries:
   `SELECT pid, now()-query_start AS age, query FROM pg_stat_activity
    WHERE state='active' ORDER BY age DESC LIMIT 10;`

## Mitigation

If a deploy correlates, roll it back — see the rollback runbook.

If a single slow query is holding connections, terminate it with
`SELECT pg_terminate_backend(<pid>);`. Do this before scaling anything.

Do **not** raise `max_connections` on the primary as a first response. It moves
the failure from the pool to the database's memory, which fails harder and
recovers more slowly.

## Escalation

If connections are not recovering ten minutes after mitigation, escalate to the
Checkout team's secondary on-call and to the database on-call together. See the
escalation policy.
