# Runbook: checkout-api — High CPU

## Symptoms

Sustained CPU above 85% on checkout-api pods for more than five minutes.
Request latency on `/cart` and `/checkout` climbs above the 400ms p95 target.
The `checkout-api-cpu-high` alert fires in PagerDuty. Horizontal pod autoscaling
may already have scaled the deployment to its ceiling of twelve replicas without
bringing utilisation down.

## First checks

1. Check the deploy log for a recent release. `kubectl rollout history deploy/checkout-api`.
   The large majority of CPU incidents on this service follow a deploy within the previous hour.
2. Open the checkout-api Grafana board and compare CPU against request rate. If CPU has
   risen while request rate has stayed flat, the cause is the code, not the traffic.
3. Check whether the promotions flag `checkout.pricing.recalc_v2` was enabled recently.
   The v2 recalculation path is CPU-bound and has caused this twice.
4. Confirm the node pool is not oversubscribed. A noisy neighbour on the same node
   presents identically from inside the pod.

## Diagnosis

Take a CPU profile from one hot pod:

```
kubectl exec -it <pod> -- py-spy record -o /tmp/profile.svg --pid 1 --duration 30
```

Look for time concentrated in pricing recalculation, JSON serialisation of large
carts, or regular-expression matching in request validation. Those three account
for most CPU regressions we have seen in this service.

## Mitigation

If a deploy correlates, roll it back — see the rollback runbook. Rollback is
preferred over scaling, because scaling a CPU-bound regression raises cost
without fixing latency.

If a feature flag correlates, disable the flag. This takes effect within thirty
seconds and does not require a deploy.

If neither correlates and traffic is genuinely elevated, raise the HPA ceiling
temporarily and open a capacity ticket.

## Escalation

If CPU is not recovering fifteen minutes after mitigation, escalate to the
Checkout team's secondary on-call. See the escalation policy for the paging
chain and the timings.
